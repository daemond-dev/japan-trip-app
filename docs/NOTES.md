# Japan trip app: build notes

Notes for any Claude session working on this trip app, in Claude Code or in a claude.ai chat. Read this before changing the page (`app/index.html`), the Android code (`android/`) or the data model (`data/`), and keep it current: it is the record of how the app is put together.

Origin: the "Japan 2026" app built in a claude.ai Project in Oct–Nov 2026 for a trip around a wedding in Kyoto, turned into this template on Nov 3, 2026 with the features and none of the original trip's plans. Page version 1.

The page runs in three modes and every feature must work in all of them or degrade visibly: live (a published claude.ai artifact; `window.claude.use` gives it the database, Ask, downloads, connectors), offline (inside the Android app: `shim.js` serves bundled or saved data and `window.TripApp` is the native bridge) and static (the same files served as a plain website such as GitHub Pages: `shim.js` with no `TripApp`; `window.__APK.static` is true, Ask, +Day, dragging and sync are off, and the menu says "Shared copy built …").

## How the owner wants this work done

Confirm these with the owner in the first session and update this section.

- Plain, direct prose. No praise or agreement openers, no filler.
- Test before calling something done. Run the page against real data at a real time of day (for example, a day that is half over) before publishing.
- Base features the app is expected to keep without being asked: Today leads with what's now and what's next, finished items get out of the way, failures are visible instead of silent, the app matches whatever the owner uses as the plan.
- Only change what was asked. If something else looks wrong, say so and ask.
- Keep the app in step with the plan. When a booking, ticket or plan change comes in, update the plan document, the calendar (if the owner keeps one) and the app, or say which ones you did not touch.
- Times are Japan time, 24-hour. Prices in yen with USD in parentheses. The header clock shows home time (`meta.homeTz`, an IANA zone; Pacific time to start), because the phone's own clock already shows Japan time.
- Every feature change targets all three modes: the claude.ai artifact (also used on iPhones; there is no iOS app), the static site, and the Android app (online and offline). Run `python3 scripts/test_page.py live`, `offline` and `static`, add native support if the feature needs it (new link types, files, capabilities the shim doesn't cover), then rebuild the APK with a bumped version.
- iOS gets the claude.ai version. Keep it at feature parity and robust: anything that uses an Android-only bridge (`TripApp`, `NihongoApp`) needs a working web fallback, touch handling must work in Safari (pointer events plus a non-passive `touchmove`, no reliance on `contextmenu` or vibration), app links need a visible web fallback, and speech uses the phone's own voice. Testing so far is Chromium only.
- Food allergies and party details live in data, never in code: `meta.travelers`, the phrases with "~" blanks (Core, Restaurant, Ryokan and hotel, Small talk) and the packs in `data/packs/` (see "Personalizing a copy" below).

## Map of the system

- Repo layout: `app/index.html` (the page), `data/*.json` (one file per database document; `data/packs/` holds optional phrase packs), `android/` (the APK source, templated from `android/local.properties`), `scripts/` (`build_static.py`, `make_data.py`, `patch_html.py`, `add_pack.py`, `make_keystore.py`, `test_page.py`), `site/` (generated static site, not committed), `.github/workflows/` (`test.yml` runs the page tests on every push and PR; `pages.yml` publishes the site; `apk.yml` builds and releases the Android app on demand), `.claude/commands/` (slash commands for Claude Code), `docs/` (these notes, the claude.ai setup prompt, the handoff prompt), `requirements.txt` (Python tools).
- This repo's static site: https://ricky.biz/japan-trip-app/ (GitHub Pages with the account's custom domain; enabled Nov 3, 2026, build type workflow). Repo: https://github.com/daemond-dev/japan-trip-app (private; the Pages site is still readable by anyone with the link).
- Cloud-first: the repo is meant to be worked on from Claude Code on the web or in the Claude mobile app, with GitHub Actions doing tests, the site and the APK. A sandbox may not reach the Playwright CDN or `dl.google.com`; then the workflows are the test and build path.
- Live app: a published claude.ai artifact of `app/index.html`, data in the artifact's database, seeded from `data/`. URL: (fill in after the first publish). Private; shared through the artifact's Share menu, as Editor so people can tick to-dos. Publishing and database writes are claude.ai chat tools, not Claude Code tools: see `docs/SETUP-IN-CLAUDE.md`.
- Static site: `python3 scripts/build_static.py` writes `site/` (page + `data.js` + `shim.js` + `manifest.webmanifest`, `sw.js`, icons); the workflow publishes it with GitHub Pages on every push to `main`. It installs from the browser's "Add to Home Screen" on iPhone and Android and opens offline: the service worker precaches the site and serves network-first with a 5 s timeout, cache as the fallback, so it is fresh when online and still opens without a connection. Sync now on a static copy is a reload. Public to anyone with the link, so `data/` on a shared repo must not hold confirmations, QR codes or private contact details.
- One self-contained HTML file, vanilla JS, no build step, no web fonts (system fonts; `--sign` is the system UI font, `--sans` prefers Hiragino Sans and Noto Sans JP).
- Capabilities to declare on a publish that passes `capabilities` (restate the full set every time, because a non-empty object replaces the stored declaration): `{"db":{}, "user":{}, "downloads":true, "sample":{"images":true}, "mcp":{"servers":[{"server":"Mapbox","tools":["search_and_geocode_tool"]},{"server":"Rome2Rio","tools":["get-routes"]}]}}`. `mcp` only works for a viewer who has those connectors connected in claude.ai; the page copes with `null` (the feature stays off). Omitting `capabilities` on a republish carries the stored set forward.
- Content lives in data, not in the page code: in the artifact database for the live app (the page subscribes to it and caches the last copy in the phone's localStorage; booking pages are cached in IndexedDB (`jt-docs`) and, in the Android app, in the app's own files), in `data/` for the static site and the bundled offline copy. For a live copy, `data/` is the seed and a backup, not the source of truth once the artifact is seeded: the database wins, and a claude.ai chat can export it (`read_db` with `out_dir`) back into `data/`.
- Source of truth for the plan: whatever the owner keeps (a document, a calendar). Record it here once known. "Sync the app" means: read it, update the data to match, refresh `meta.rate` (yen per USD) and `meta.weather` (daily forecast for the day's city), set `meta.updatedAt`, then publish (live: write the docs; static: push).

### Tabs and features

- Today: hero with city, weather line(s) from `meta.weather`, the Sleep card (tap it to open that stay's booking on Reservations, with the day picked) and a driver-card button. Lines under it: "Now <time> <title>, until HH:MM" for an item in progress, "Next <time> <title>, in N min" for the next timed item, "Later today: ..." for untimed items still ahead when nothing timed is next, and "Tomorrow <time> <title>" only when nothing is left today or it's 21:00 or later (Sleep and Task items are skipped as tomorrow's preview). A To do block lists items due that day plus, on today, anything overdue. Items that are over fold into "Show past items." Tapping an item's badge marks it past or brings it back; marks are shared between phones through `trip/pastMarks` when connected and kept on the phone (localStorage `jt-past`) until the next connected open pushes them. The day rolls over at midnight Japan time unless a day was picked by hand. With no days in `trip/days` the tab says "No itinerary yet."
- Reservations (`#reservations`, reached from the Places tab's header toggle): a stay shows on every night it covers and stays current ("Staying now") until checkout; stay cards carry `id="res-stay-<id>"` for the Sleep-card jump. Two modes. Booked lists every booked meal, travel leg, activity and stay, grouped by date. Not booked yet lists open meal times (`mealOpen`, which fold at 10:30, 14:30 and 22:30), Pending or Not booked meals, and planned travel or stays not booked. Filters: All, Meals, Travel. Anything already over folds into "Show past."
- Trip overview (menu button "Trip overview, to-do and tips", `#trip`; not a tab): day overview (skips Sleep and Task items), stays with bookings, shared to-do list, tips. Overdue to-dos are flagged, and the menu button shows a count of to-dos overdue or due today. Shows stays, to-dos and tips even while the itinerary is empty.
- Places: a search box (name, Japanese, romaji, area, station, note), then filters for city, Area within the city (`district`) and Type (`cat`); they combine. Each place shows a day tag when it's on the plan, Google Maps search and transit-directions links by place ID, driver card and Call buttons, and a distance or travel-time estimate from where you are (see "Travel times" below). A button opens the shared Google Maps list when `meta.mapsListUrl` is set (it isn't yet; make a Google Maps list and set it). "+ Day" adds a place to a day (see below). "Mark visited" hides a place; "Show visited (N)" brings them back dimmed.
- Yen: converter using `meta.rate`; reference prices (`trip/prices`) converted live. A personal rate override lives in Settings (localStorage `jt-rate`). The tab flags a rate 7 or more days old.
- Speak: Translate shortcuts (iOS `googletranslate://?sl=&tl=&text=`, Android `intent://` with web fallback; camera and conversation just open the app), the Numbers tool (digits, kanji, yen, people, things, floors like 2F, 3階, B1F, clock times), then search and theme buttons (All, each phrase section, Signs, Emergency; remembered with the other filters), then signs, phrase sections with play-aloud, full-screen show and copy buttons, and emergency numbers last. Search is debounced and also matches the section name. A remembered theme never hides results: if it has no match the search widens to every section, otherwise a button offers the matches in other sections. All phrase-list interaction is delegated to one set of listeners on `#speakBody` (`wireSpeakBody`), not wired per row. Phrases move by the grip, or by holding a phrase for half a second and then dragging; hold and lift opens the sections sheet.
- Ask (far right of the bottom bar; a full-screen chat, hidden when `sample` resolves null and in the offline copy): see "Ask about the trip" below.
- Menu (top left): Sync now; connection status (an orange dot on the menu button means not connected, showing the saved copy); Save offline copy and Save offline copy with confirmations (static HTML through `downloads`, no scripts so it opens in the iPhone's Files preview; the second embeds every booking page as an image and needs a connection); Settings (theme, own yen rate, the saved copy's size and time plus how many booking pages are kept for offline, reset this phone's copy, phrase order and sections, Android app options). Pull down at the top of any tab also syncs.

### Travel times from where you are

- Origin: the phone's location (the Android app's own fix via `TripApp.getLocation`, else the browser's geolocation), or a place the user picks ("I'm at…"), else today's hotel. Every place with coordinates gets an instant distance estimate (walk under 1 km, train or subway otherwise, Shinkansen past 100 km); when the Rome2Rio connector is allowed (`mcp`, tool `get-routes`) and the page is online, real transit times for the cards on screen replace the estimates as they arrive. Nothing here is saved to the database.

## Data model

Collection `trip`:

- `meta`: `{title, homeTz, travelers, rate:{jpyPerUsd, asOf, source}, weather:{updatedAt, source, days:[{date, city, hi, lo, text, rain}]}, mapsListUrl?, updatedAt (YYYY-MM-DD), source, apkLatest}`. `title` is shown in the header and drawer; `homeTz` drives the header clock; `travelers` is a plain-text briefing for Ask (who is traveling, surname as written on bookings, party size, allergies, trip dates): keep it current. Several weather entries may share a date; Today shows every entry for the day.
- `pastMarks`: `{marks:{"<date>|<t>|<title>": true|false}}`, the shared past marks (true = marked past, false = brought back). Optional.
- `days`: `{days:[{date, city, start?, sleep, stay (place id or null), items:[...], tips:[strings], mealOpen?:[{meal, note?}]}]}`
  - item: `{t, m, end?, at?, endAt?, type, title, status, detail?:[strings], place?, links?:[{label,url}], qr?:[{label, ja?, svg}], docs?:[{id, label, pages}], addedInApp?}`. `at`/`endAt` are ISO times with an offset for anything not in Japan time (home-side flight legs); they drive Next and folding. `qr` holds a ready-made inline SVG (black on white) with a Japanese caption `ja` shown above the English one; regenerate it from the decoded text with segno and check it decodes back with zxing-cpp.
  - `t`: display time ("17:16", "10:00–18:00", "~14:00", "Evening", "14:50 PT"). Ranges may use an en dash or a hyphen.
  - `m`: start in minutes after midnight Japan time, or `null` for untimed or home-side items. `m` drives Now, Next and folding. Untimed items never fold on their own; they're listed under "Later today."
  - `end`: end in minutes; set it for anything longer than 30 minutes (trains, meals, events, a task with a deadline), or the item folds away while still happening. Ranges in `t` are parsed automatically.
  - `type`: Travel (T), Food (F), Hotel (H), Activity (A), Wedding (W), Sleep (Z), Task (!). (Wedding was the original trip's event type; it stays usable for any fixed event.)
  - `status`: Booked, Not booked, Pending, Wedding event, No reservation, Walk-up, Plan, Phone check.
  - `mealOpen`: the meal times on that day with nothing booked. Remove an entry when that meal gets booked (and add the booking as a Food item with status Booked).
  - Every day should end with a Sleep item; `stay` points at the stay's place id.
- `stays`: `{stays:[{id, name, dates, checkIn, checkOut, conf, under, lines:[strings], links?:[{label,url}], qr?, docs?}]}`. `lines` carry the pertinent details (room, payment, cancellation terms, address, phone). `under` is the surname the booking is under.
- `places`: `{groups:[{name (city), places:[{id, name, ja?, ro?, addr?, addrRo?, tel?, area, district, station, placeId, lat, lng, cat, note, hours?, floors?, floorUrl?, floorNote?, steps?, routeUrl?, needsDetails?, addedAt?, mapboxId?}]}]}`. `ja` + `addr` enable the driver card; `ro` and `addrRo` are the romaji shown under the name and address (wapuro style, "Toukyou", to match the phrases). The card's request line comes from `phrases.taxi` with romaji in `phrases.taxiRo`. Get `placeId` from a Google Maps places search. `district` is the Area filter within a city; keep it coarse. Tokyo: West (Shinjuku, Shibuya), Central (Ginza, Tokyo Station), East (Akihabara, Asakusa), Outskirts (Narita, DisneySea). Kyoto: Kyoto Station, Downtown and Gion, Outskirts (Arashiyama, Kitayama). Hakone: Hakone-Yumoto. Osaka: Tempozan. Give every new place one of these (or add a new coarse one), or it lands under "Other". `cat` drives the Type filter: Food = Restaurants, Shop = Shops, Activity = Sightseeing, Travel, Hotel = Hotels, Wedding. An item's `place` or a day's `stay` is what gives a place its day tag. Floor guides render as a building (`floorBlock`): `floors` items are objects `{f, en, ja?, map?}` or strings like `"5F: travel goods"`; `floorNote` adds a caveat line; `floorUrl:{label,url}` links the store's plan. A suggested walk can carry `steps:[strings]` and `routeUrl` (a Google Maps walking route). Example: `akiba_walk`.
- `prices`: `{groups:[{name, items:[{label, yen (number or [min, max]), note?}]}]}`
- `phrases`: `{signs:[{ja, ro, en}], groups:[{name, phrases:[{en, ja, ro, hear?, card?}]}], emergency:[{label, number}], taxi, taxiRo, synonyms:[[words...]]}`. Sections run most-used first, with a question you'll hear (`hear`) placed above its answers; `card` marks a phrase meant to be shown to staff full screen (its `ro` then holds the English gloss). `synonyms` groups the Speak search treats as interchangeable (each typed word matches itself anywhere, or any word in its group as a whole word in the English text). Current sections: Core, Pointing, Finding things, Restaurant, Paying, Seafood allergy, Kids and baby, Ryokan and hotel, Trains and taxis, Shopping, Small talk.
- `tips`: `{groups:[{name, items:[strings]}]}`
- `phrasePins` = `{ja:[...]}`: pinned phrases in their pinned order, set from the long-press sheet. Pinned phrases show in a Pinned section above everything, whatever theme is selected. Optional.
- `phraseThemes` = `{map:[{ja, add:[sections], remove:[sections]}]}`: section changes made by long-pressing a phrase. Settings has "Restore the original sections" (deletes the doc). Optional.
- `phraseOrder` = `{order:[{g, ja:[...]}]}`: the phrase order set by dragging on the Speak tab (shared). Phrases a section doesn't list keep their original position. Settings has "Restore the original order" (deletes the doc). Dragging is off while searching and in the offline copy. Optional.
- `visited` = `{ids:{placeId:true|false}}`: overrides of the automatic visited state only (a place counts as visited when it has a Booked item whose end has passed, or is a stay whose checkout has passed, and has no item still ahead). Optional.

Collection `todo`: one doc per item, `{text, due (YYYY-MM-DD), order, done, doneAt?}`. Anyone with edit access can tick items.

Collection `app`: `page` = `{version, html, savedAt}`, the current page source for the Android app's offline copy. `apksrc` = the APK source and signing key, see below.

Collection `docs`: one doc per page image of a booking confirmation, `docs/<id>-<n>` = `{mime, b64}` (JPEG, about 820 px wide, under 72 kB so batches stay under the 1 MB write limit). Items and stays point to them with `docs:[{id, label, pages}]`; the page shows them full screen, loading pages in parallel. Pages are cached in memory, in IndexedDB on the phone, and in the Android app's files (`TripApp.saveDoc`); a connected page prefetches every page once (upcoming days first), so the offline copy can show them. The viewer has a Download button that builds one PDF from the page images (`pagesToPdf`, no library): in the Android app through `TripApp.saveFile`, in the browser and the Claude iOS app through the `downloads` capability. When the owner shares a booking confirmation: add the stay or item (details, manage/cancel link, any QR code), render the confirmation's pages to JPEGs and write them to `docs`.

## Updating

- In Claude Code: edit `data/*.json` and `app/index.html` in the repo, run `python3 scripts/test_page.py live`, `offline` and `static`, commit, push (the workflow republishes the static site). Validate JSON after every data edit.
- In a claude.ai chat (the live app): data: Artifact `read_db` (get the doc) first, edit, then `write_db` `set` with `if_version` from the read; other sessions also write there, so never write from an old copy; use `batch` for several docs. Page: Artifact `read` the live page first, then Artifact `edit` with old/new pairs for small changes, or publish the whole file with `url` for big ones. Pass `capabilities` only when adding one, and then the full set (under "Map of the system"). Every publish needs the owner's approval. **After every page change, write the new page source to `app/page` with a higher `version`** so the Android app picks it up on its next online open. Then commit the same page to the repo so the two stay identical.
- Test before publishing anywhere: `scripts/test_page.py` loads the page in Playwright with a stub runtime, in all three modes and both color schemes, and reports console errors. Fake `Date.now` to the moment you care about when checking Today.
- After a data change, connected phones update on their own (live) or at the next site publish (static); the Android app shows its bundled copy only when offline.

## Phone app (APK)

- `<AppName>-<version>.apk` (from `APP_NAME` and the version passed to `build.sh`), Android only. Online it shows the live artifact in a WebView, so it stays in sync; offline it shows a bundled copy of the page fed by the last data the live page handed over. On an online start the saved copy shows at once in a second WebView while the live page loads underneath, and is dropped when the page reports `TripApp.liveReady()` (after the trip frame is pinned), on a load error, or 20 s after a page without the frame (sign-in).
- The live page talks to the app through `window.TripApp` only when it exists: `saveData` (every data change), `getLocal`/`saveLocal` (theme, own yen rate, past marks, filter choices on Reservations and Places, and the last spot: tab, scroll position, day picked on Today), `takePending` (to-do ticks made offline, applied on the next live open), `setBright` (full brightness while a QR code is on screen), `saveDoc`/`getDoc`/`docCount` (booking pages for the offline copy), `copy` (clipboard), `netState` ("online", "captive", "noinet", "none"), `openTranslate(sl, tl, mode)`, `setChrome` (show or hide the claude.ai bar), `saveFile(name, base64)` (writes to Downloads/Japan 2026 and opens it), `getLocation`/`requestLocation`, `setWantsBack`/`ackBack` (Back button), `savePage`/`pageVersion` (offline page updates). Keep those calls working when you change the page.
- Plan changes and page changes need no rebuild. The live page reads db doc `app/page` ({version, html}) and hands it to the app (`savePage`), which serves it offline with `data.js` and `shim.js` injected after the first `<head>`. Rebuild only when the Java code or `shim.js` changes, and bump `meta.apkLatest` so the menu tells the owner a new APK is waiting.
- The page holds its own Android behavior (it checks `window.__APK`, set by `shim.js`); `patch_html.py` only adds the offline scripts after the page's first `<head>` when building the fallback copy.
- Back button: the page keeps a stack of the views you came from (`tabStack`) and closes overlays first (`appBack`). Offline, the app calls `window.__apkBack` directly. Live, the page reports `TripApp.setWantsBack(bool)` only when the answer changes, the app passes a press in by posting the window message `jt-back` into the trip page, and the page answers `TripApp.ackBack()`; no answer within 700 ms falls back to normal Back.
- Network: a `ConnectivityManager` callback switches an offline-showing app to live when a validated connection appears (at most once a minute, with a toast). The page itself probes `trip/meta` after more than 3 minutes in the background and listens to the browser's online/offline events.
- A non-passive `touchmove` listener stops the page scrolling while a phrase is held or dragged; without it Android cancels the drag. It is attached only while the Speak tab is open (`blockOn`/`blockOff`), because it makes every scroll wait for the page.
- Cloud build: the "Build the Android app" workflow (`apk.yml`, Actions tab > Run workflow) takes a version and the live URL (the Pages site, or an artifact link), builds with the same `build.sh`, uploads the APK as a workflow artifact and publishes it on the Releases page (`releases/tag/v<version>`). It signs with the repo secrets `SIGNING_KEYSTORE_B64` (base64 of the keystore), `SIGNING_ALIAS` and `SIGNING_PASS`; `scripts/make_keystore.py` creates all three without Java. With no secrets it signs with a throwaway key and warns.
- Source lives in `android/`. `build.sh` reads `android/local.properties` (package name `APP_ID`, launcher label `APP_NAME`, `LIVE_URL`, keystore settings), templates `AndroidManifest.xml`, `src/MainActivity.java` and `res/values/strings.xml` from it, generates the bundled page and data from `../app` and `../data`, and creates the keystore on the first build. The keystore and `local.properties` are gitignored: keep the keystore somewhere safe, because an update signed with a different key is refused (the app would have to be uninstalled, which wipes its saved ticks). `LIVE_URL` is the claude.ai artifact for the full app, or the GitHub Pages URL for a static-only app that updates when the site is republished (`STATIC_LIVE` in `MainActivity.java`, set when the URL isn't on claude.ai: the app treats the site as the page itself, no frame to pin, splash dropped on load, `setChrome` a no-op, the site's host allowed in the WebView; `TripApp.isStaticHost()` tells `shim.js` it is the live static copy, and the shim hands the site's data to the app with `saveData` so the bundled offline copy shows the latest data next time; page code in that offline copy only changes with a rebuild).
- Toolchain (worked on Linux and in a claude.ai chat container): Android command-line tools from dl.google.com (`commandlinetools-linux-11076708_latest.zip`), `sdkmanager --licenses` first in the foreground, then `sdkmanager "platforms;android-35" "build-tools;35.0.0"`, ecj 3.38.0 from Maven Central, OpenJDK 17 or 21, `zip`, no Gradle. About five minutes end to end. `SDK` and `ECJ` environment variables point `build.sh` at them.
- Camera and file picker: a WebChromeClient `onShowFileChooser` lets `<input type="file">` work (photos for Ask), writing camera shots to Pictures/Japan 2026 through MediaStore.

## Ask about the trip (in-app chat)

- Calls Claude through the `sample` capability. Before each send it reads `permissions.state("sample")`: denied shows a Permissions button (`permissions.manage()`); prompt in the Android app temporarily shows the claude.ai page (`TripApp.setChrome(true)`, restored after), because the claude.ai consent prompt otherwise sits behind the app.
- Two modes. With page tools (`sample.limits().tools`): lookups `get_day`, `get_place`, `find_places`, `find_phrases` plus one `stage_changes` tool taking `[{op, args}]`. Without them: the prompt carries the full trip data as JSON and Claude ends its answer with `CHANGES: [...]`, which the page parses. Both run the same OPS: `update_item`, `add_item`, `remove_item`, `add_place`, `update_place`, `remove_place`, `add_phrase`, `update_phrase`, `remove_phrase`, `add_tip` (listed in `ASK_OPS_HELP`).
- The briefing (`askOverview`) starts with `meta.travelers`, so Ask knows the party and the allergy; `ASK_INSTR` tells it to keep allergies in mind for food.
- Staged changes go into a draft and a "Proposed changes" card; Apply writes whole docs with `db.doc("trip/<doc>").set`, then offers Undo. Booked and wedding-type items can't be removed; hotels can't be removed from Places; places added here have no `placeId`.
- Photos: the camera button (shown only when `sample.limits().images` exists) picks or takes photos, sent with that one message only. The conversation is kept per device (`jt-ask` in localStorage); New clears it.
- `add_place` from Ask saves `needsDetails:true` and `addedAt`, with no `placeId`; the card shows "Details pending". Instant fill-in uses the Mapbox connector (`mcp`, `search_and_geocode_tool`) with a Japanese query (`ja`) and `language:"ja"`; English queries for Japanese shops returned nothing, so Ask is told to pass `ja`. Mapbox gives the Japanese name, address and coordinates, not phone or hours. In the Android app the first connector use asks for consent behind the app; the page reveals the claude.ai page when `permissions.state("mcp")` is "prompt".
- **At the start of a chat about the app, check `trip/places` for `needsDetails`.** For each one: Google Maps places search (name plus area), then set `placeId`, `lat`, `lng`, `station`, `district`, an hours/phone line in `note` if useful, `ja` + `addr` with `ro` + `addrRo` romaji so it gets a driver card, and `tel`; then delete `needsDetails`. Tell the owner which places were filled in and anything that couldn't be matched.
- Place cards have a "+ Day" button (hidden offline) that writes `trip/days` with a new item `{t, m, end:m+60, type from place cat, title, status:"Plan", place, detail?, addedInApp:true}`. **At the start of a chat about the app, look for `addedInApp:true` items in `trip/days`:** copy each to the owner's plan document and calendar, then delete the flag, and say which ones were copied.

## Personalizing a copy

Everything personal is data. `/setup` (in `.claude/commands/setup.md`) walks through it:
- `meta.title`, `meta.homeTz` (IANA zone for the header clock), `meta.travelers` (plain-text briefing for Ask: who is traveling, surname as written on bookings, party size, allergies, trip dates).
- Phrases with "~" blanks: Core "I'm ~", Restaurant "~ people", "reservation under ~", "Can ~ of us get in?", Ryokan and hotel "reservation under ~", Small talk "We're from ~". Fill the surname in katakana (write it the way the person says it: "BASH-or" → バショア, "Yamasu" → ヤマス) and update `ro` to match.

## Gotchas already hit (keep these fixed)

- A `.wrap` padding rule overrode `main`'s bottom padding, so the bottom bar hid the last content.
- Connection failures were swallowed silently, so a dropped connection looked like "the app isn't updating." Now shown with the menu dot and status text.
- Today did not hide finished items and did not roll to the next day if left open. Both fixed; keep it that way.
- Items without `end` folded 30 minutes after start. Set `end` on anything long.
- The "Tomorrow" preview used to appear whenever nothing timed was still ahead. Now gated on Now, Next and Later today.
- Published pages can't fetch other sites, so the yen rate and the weather are written into `meta` by Claude, and maps are links, not embeds.
- `scrollIntoView` on the chip rows also scrolled the page, which undid the restored scroll position on reopen. Chip rows scroll sideways with `hScroll` instead.
- Viewer-reserved URL hash tokens (settings, sidebar, customize, upgrade, downloads, comment-*) can't be used for in-page links.
- Every db snapshot used to trigger a full render. Renders are coalesced in `scheduleRender` and unchanged documents (same frozen object) are skipped.
- A non-passive `touchmove` on `document` made every scroll on every tab wait for the main thread. Keep it scoped to Speak.
- When editing the page with text anchors, `/* trip tab */` and `<head>` each appear twice (the CSS has a `/* trip tab */` comment and the offline-copy template inside the script has its own `<head>`). Anchor on the JS line (`/* trip tab */\nlet canWrite`) and the first `<head>`.
